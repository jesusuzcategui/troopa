Troopa documentation

Troopa is a terminal app to plan work, hand each task to an AI coding agent in its own git worktree, review the result and merge it. Everything lives in one SQLite file and one config.toml.

Getting started

  1. Install Troopa (install options) and at least one agent CLI: Claude Code, Codex, OpenCode, Cursor or Pi.
  2. Run troopa. The first run asks for language, theme, default agent, editor, terminal, merge strategy and the second brain folder. Run it again with troopa setup, or change anything later with S.
  3. Press n to create a project and point it to a git repository. If the folder does not exist, Troopa creates it with git init.
  4. Press enter to open its board, n to add a task, and move it to ready to launch its agent.

Press ? anywhere for the shortcuts of that screen and Ctrl+K for the command palette.

Projects and board

A project is a git repository. Its tasks move through inbox → backlog → ready → in-progress → review → done (plus blocked and pair-paused). Switch between board and list with v, fold statuses with z, open the task panel with tab.

Each task has a title, a description in Markdown, acceptance criteria (one per line), priority, agent, model, mode (yolo or pair), commit mode and type. Attach files with a and reference repo files with @path.

Clients (c on the project list) group projects; metrics (M) compare time, tokens and cost per agent and project.

Agents and runs

Moving a task to ready asks for confirmation and then:

  • creates a branch and a worktree under ~/.local/share/troopa/worktrees/<project>/,
  • writes TASK.md with the task, your profile, the project context and the rules,
  • starts the agent in the background. It keeps working if you close Troopa; Troopa picks it up when it opens again.

Yolo runs the agent alone and shows its live log. Pair opens the agent in a terminal next to you (TDD: red, green, refactor). When the agent ends, Troopa runs the project checks and moves the task to review or blocked.

If an agent stops before finishing (the computer turned off, for example), the run is marked blocked with a note; press x to send it back and continue.

Review and changes

The review screen shows the summary (it starts with “How to run”), the checks and the diff. Move through the diff with j/k, comment a line with enter, and press x to send your feedback and comments back to the same agent in the same worktree. Each launch and each request is a round; older rounds fold away.

  • y approve: with commits = auto it commits, pushes and opens a PR when there is a remote.
  • g merge an approved local branch into the base (squash or merge commit).
  • c clean the worktree and keep the branch · d discard both.

Plans

A plan is an ordered list of tasks of a project that run one after the other. Press w on a board to see its plans.

  1. n creates a plan: title, goal, default agent and model, and auto-advance.
  2. Add the steps in order with a (enter adds, esc ends). Reorder with K/J; enter edits a step like any task.
  3. s starts the plan: the first step that is not done launches.
  4. Each step goes through the normal review. Approving a step commits it on its branch, and the next step starts from that branch, so it builds on the work before it. With auto-advance on, it starts by itself; otherwise press s.
  5. When every step is done, open the plan and press g: the last branch (the whole plan) is merged into the branch the plan started from, or pushed with a PR when the repo has a remote. The step worktrees are removed.

Auto-approve (A, or in the plan form) lets a plan run alone: when a step's agent finishes and every check of troopa.toml passes, the step is approved and the next one starts. If a step fails, the plan stops there as blocked (the blocked hook can tell you), and after x fixes it the plan goes on. The merge at the end is always yours. Give the project real checks (tests, linters) before you turn it on: they are what decides.

p pauses (the running step finishes, the next one waits), t toggles auto-advance. A step that is blocked stops the plan until you fix it with x. Steps never merge on their own.

Profiles

A profile tells the agents who they work for. It is not only for developers: create one per profession you have (developer, chef, designer, accountant, writer, HR…). Each profile has a name, a profession, an “about” text and standing instructions.

Open them from Settings (S → Profiles) or the palette. * marks the default profile; a project can pick another one in its form (←/→ on Profile). The profile is written into every TASK.md under “Who you work for”:

## Who you work for

You are working for Ana (Chef). Use the words, standards and tools of that profession.

Runs a bakery with two stores.

Their standing instructions:

Metric units. Recipes for 12 portions.

Accounts

Accounts let agents run with a different login per project, for example a company subscription for a client and your personal one for everything else. Each account keeps its own login folder for every agent, so signing in to one never touches the other.

# ~/.config/troopa/config.toml
default_account = ""          # "" = the agents' normal login

[accounts.acme]
# dir = "~/.troopa-accounts/acme"   # optional; default ~/.config/troopa/accounts/acme
# env = { ANTHROPIC_API_KEY = "…" }  # optional extra variables

Sign each agent in once, then pick the account in the project form (Account):

troopa login acme claude
troopa login acme codex

Troopa sets CLAUDE_CONFIG_DIR (Claude Code), CODEX_HOME (Codex), XDG_DATA_HOME (OpenCode) and PI_CODING_AGENT_DIR (Pi) to the account folder. If your agent reads another variable, set it in env.

Second brain

A Markdown folder (Obsidian-friendly) that Troopa keeps up to date: inbox.md, today.md, projects/INDEX.md and, per project, project.md, tasks/ and guides/ (how to run what was merged). The agent gets the project note as context. Browse it with B, search with /, add to the inbox with i. Set brain_git = true for local commits.

Graph

Press G in the brain to see it as a graph, drawn in the terminal with braille dots. The local view puts the open note in the middle with its links around it: ←/→ pick a note, enter centers on it (and opens it when it is already the center), 1/2 show one or two rings of links. v switches to the whole brain, laid out by a force simulation: arrows move to the nearest note, +/- or the mouse wheel zoom, 0 fits everything. Tasks and guides are tied to their project even without a written link. A click selects a note; a second click opens it.

Hooks

Hooks are shell commands that run on events: task_created, launch, review, blocked, approve, merge, discard, plan_start, plan_done. Put them in config.toml (every project) or in the project's troopa.toml. An event takes one command or a list.

[hooks]
review = "notify-send 'Troopa' \"$TROOPA_TASK is ready for review\""
approve = ["./scripts/deploy-staging.sh", "curl -s -X POST $SLACK_URL -d @-"]

Each hook gets the event as JSON on stdin and in variables: TROOPA_EVENT, TROOPA_PROJECT, TROOPA_REPO, TROOPA_TASK_ID, TROOPA_TASK, TROOPA_STATUS, TROOPA_AGENT, TROOPA_RUN_ID, TROOPA_BRANCH, TROOPA_WORKTREE, TROOPA_PLAN_ID, TROOPA_PLAN. Hooks run in the background (2-minute limit) inside the worktree or the repo, and their output goes to ~/.local/share/troopa/hooks.log.

Extensions

Any program named troopa-<name> on your PATH becomes troopa <name>, like git subcommands. Write it in any language. It receives the arguments and TROOPA_BIN, TROOPA_CONFIG, TROOPA_DATA, TROOPA_DB and TROOPA_VERSION, and can read or change Troopa's data through the JSON CLI.

#!/bin/sh
# ~/.local/bin/troopa-standup: tasks in review, as a list
"$TROOPA_BIN" task list --json --status review | jq -r '.data[] | "- " + .title'

troopa extensions lists the ones it finds. Built-in commands cannot be replaced.

Daemon

troopa daemon is a long-running process without the TUI. Every few seconds it looks at running agents, finishes a run when the agent has exited, and starts the next step of a plan that has auto-advance. Logs go to $XDG_DATA_HOME/troopa/daemon.log. A pid file keeps a second daemon from starting. The TUI keeps working with or without it.

troopa daemon
troopa daemon status
troopa daemon install
troopa daemon uninstall

install writes a systemd user unit on Linux (~/.config/systemd/user/troopa.service) and a launchd agent on macOS (~/Library/LaunchAgents/dev.troopa.plist), then enables it. uninstall removes that file. Windows is not supported yet. status prints whether it is running and the runs it watches.

JSON CLI

Every resource has a versioned JSON command (schema_version 1) that uses the same store as the TUI:

troopa project list --json
troopa task create --json --project 1 --title "Add search" --agent codex
troopa plan create --json --project 1 --title "Checkout" --agent claude
troopa plan add-step --json --id 1 --title "Cart page"
troopa profile create --json --name Ana --profession Chef
troopa run rounds --json --id 3
troopa brain sync --json

Resources: project, client, task, run, plan, profile, brain. The full reference is in docs/cli-json.md.

Configuration

~/.config/troopa/config.toml (the Settings screen edits the common keys and keeps your comments):

language = "en"            # en, es or auto
theme = "catppuccin-mocha"
default_agent = "claude"
default_model = ""
default_account = ""
default_profile = 1
editor = "nvim"
terminal = ""              # auto
merge = "squash"           # squash or merge
branch_prefix = ""
worktrees = ""             # default ~/.local/share/troopa/worktrees
brain = "~/brain"
brain_git = false

[agents.claude]
command = "claude"
args = ["-p", "{{prompt}}", "--dangerously-skip-permissions", "--output-format", "stream-json"]

[prices.claude]            # USD per million tokens
input = 3
output = 15

[accounts.acme]

[hooks]
review = "notify-send Troopa \"$TROOPA_TASK\""

Each repo can have a troopa.toml with project rules:

checks = ["go test ./...", "go vet ./..."]
instructions = """
Use the existing components. Write tests for every handler.
"""

[hooks]
merge = "./scripts/deploy-staging.sh"

Documentación de Troopa

Troopa es una app de terminal para planear el trabajo, darle cada tarea a un agente de IA en su propio worktree de git, revisar el resultado y hacer merge. Todo vive en un archivo SQLite y un config.toml.

Primeros pasos

  1. Instala Troopa (opciones de instalación) y al menos un agente: Claude Code, Codex, OpenCode, Cursor o Pi.
  2. Ejecuta troopa. El primer arranque pregunta idioma, tema, agente por defecto, editor, terminal, estrategia de merge y la carpeta del segundo cerebro. Repítelo con troopa setup o cambia todo después con S.
  3. Pulsa n para crear un proyecto y apúntalo a un repositorio git. Si la carpeta no existe, Troopa la crea con git init.
  4. Pulsa enter para abrir su tablero, n para agregar una tarea y muévela a ready para lanzar su agente.

Pulsa ? en cualquier pantalla para ver sus atajos y Ctrl+K para la paleta de comandos.

Proyectos y tablero

Un proyecto es un repositorio git. Sus tareas pasan por inbox → backlog → ready → in-progress → review → done (más blocked y pair-paused). Cambia entre tablero y lista con v, pliega estados con z y abre el panel de la tarea con tab.

Cada tarea tiene título, descripción en Markdown, criterios de aceptación (uno por línea), prioridad, agente, modelo, modo (yolo o pair), modo de commits y tipo. Adjunta archivos con a y referencia archivos del repo con @ruta.

Los clientes (c en la lista de proyectos) agrupan proyectos; las métricas (M) comparan tiempo, tokens y costo por agente y por proyecto.

Agentes y ejecuciones

Al mover una tarea a ready, Troopa pide confirmación y luego:

  • crea una rama y un worktree en ~/.local/share/troopa/worktrees/<proyecto>/,
  • escribe TASK.md con la tarea, tu perfil, el contexto del proyecto y las reglas,
  • arranca el agente en segundo plano. Sigue trabajando aunque cierres Troopa; Troopa lo retoma al abrirse.

Yolo ejecuta el agente solo y muestra su log en vivo. Pair abre el agente en una terminal a tu lado (TDD: rojo, verde, refactor). Cuando el agente termina, Troopa corre los checks del proyecto y mueve la tarea a review o blocked.

Si un agente se detiene antes de terminar (por ejemplo, se apagó el equipo), la ejecución queda en blocked con una nota; pulsa x para devolvérsela y continuar.

Revisión y cambios

La pantalla de revisión muestra el resumen (empieza con “How to run”), los checks y el diff. Recorre el diff con j/k, comenta una línea con enter y pulsa x para mandar tus comentarios al mismo agente en el mismo worktree. Cada lanzamiento y cada pedido de cambios es una ronda; las anteriores se pliegan.

  • y aprobar: con commits = auto hace commit, push y abre un PR si hay remoto.
  • g merge de una rama local aprobada en la base (squash o merge commit).
  • c limpiar el worktree y conservar la rama · d descartar ambos.

Planes

Un plan es una lista ordenada de tareas de un proyecto que se ejecutan una tras otra. Pulsa w en un tablero para ver sus planes.

  1. n crea un plan: título, objetivo, agente y modelo por defecto, y avance automático.
  2. Agrega los pasos en orden con a (enter agrega, esc termina). Reordena con K/J; enter edita un paso como cualquier tarea.
  3. s inicia el plan: se lanza el primer paso que no esté terminado.
  4. Cada paso pasa por la revisión normal. Al aprobar un paso se hace commit en su rama y el siguiente arranca desde esa rama, así construye sobre el trabajo anterior. Con avance automático arranca solo; si no, pulsa s.
  5. Cuando todos los pasos están listos, abre el plan y pulsa g: la última rama (el plan completo) se mergea en la rama desde la que empezó el plan, o se hace push con PR si el repo tiene remoto. Los worktrees de los pasos se eliminan.

La aprobación automática (A, o en el formulario del plan) deja que el plan corra solo: cuando el agente de un paso termina y todos los checks de troopa.toml pasan, el paso se aprueba y arranca el siguiente. Si un paso falla, el plan se detiene ahí en blocked (el hook blocked te puede avisar), y cuando lo arreglas con x el plan sigue. El merge final siempre es tuyo. Dale al proyecto checks de verdad (tests, linters) antes de activarla: son los que deciden.

p pausa (el paso en curso termina y el siguiente espera), t activa o desactiva el avance automático. Un paso bloqueado detiene el plan hasta que lo arregles con x. Los pasos nunca hacen merge por separado.

Perfiles

Un perfil le dice a los agentes para quién trabajan. No es solo para programadores: crea uno por cada profesión que tengas (programador, chef, diseñador, contador, escritor, recursos humanos…). Cada perfil tiene nombre, profesión, un texto “sobre ti” e instrucciones fijas.

Ábrelos desde Configuración (S → Perfiles) o la paleta. * marca el perfil por defecto; un proyecto puede elegir otro en su formulario (←/→ en Perfil). El perfil se escribe en cada TASK.md bajo “Who you work for”:

## Who you work for

You are working for Ana (Chef). Use the words, standards and tools of that profession.

Runs a bakery with two stores.

Their standing instructions:

Metric units. Recipes for 12 portions.

Cuentas

Las cuentas permiten que los agentes usen un login distinto por proyecto, por ejemplo la suscripción de una empresa para un cliente y la tuya personal para lo demás. Cada cuenta guarda su propia carpeta de login por agente, así iniciar sesión en una nunca toca la otra.

# ~/.config/troopa/config.toml
default_account = ""          # "" = el login normal de los agentes

[accounts.acme]
# dir = "~/.troopa-accounts/acme"   # opcional; por defecto ~/.config/troopa/accounts/acme
# env = { ANTHROPIC_API_KEY = "…" }  # variables extra opcionales

Inicia sesión una vez con cada agente y elige la cuenta en el formulario del proyecto (Cuenta):

troopa login acme claude
troopa login acme codex

Troopa apunta CLAUDE_CONFIG_DIR (Claude Code), CODEX_HOME (Codex), XDG_DATA_HOME (OpenCode) y PI_CODING_AGENT_DIR (Pi) a la carpeta de la cuenta. Si tu agente usa otra variable, ponla en env.

Segundo cerebro

Una carpeta Markdown (compatible con Obsidian) que Troopa mantiene al día: inbox.md, today.md, projects/INDEX.md y, por proyecto, project.md, tasks/ y guides/ (cómo correr lo que se mergeó). El agente recibe la nota del proyecto como contexto. Recórrelo con B, busca con / y agrega al inbox con i. Con brain_git = true hace commits locales.

Grafo

Pulsa G en el cerebro para verlo como grafo, dibujado en la terminal con puntos braille. La vista local pone la nota abierta en el centro con sus enlaces alrededor: ←/→ eligen una nota, enter la centra (y la abre si ya es el centro), 1/2 muestran uno o dos anillos de enlaces. v cambia a todo el cerebro, acomodado con una simulación de fuerzas: las flechas van a la nota más cercana, +/- o la rueda del ratón hacen zoom y 0 ajusta todo. Las tareas y guías quedan unidas a su proyecto aunque no tengan un enlace escrito. Un clic elige una nota; un segundo clic la abre.

Hooks

Los hooks son comandos de shell que corren en eventos: task_created, launch, review, blocked, approve, merge, discard, plan_start, plan_done. Ponlos en config.toml (todos los proyectos) o en el troopa.toml del proyecto. Un evento acepta un comando o una lista.

[hooks]
review = "notify-send 'Troopa' \"$TROOPA_TASK está lista para revisar\""
approve = ["./scripts/deploy-staging.sh", "curl -s -X POST $SLACK_URL -d @-"]

Cada hook recibe el evento como JSON por stdin y en variables: TROOPA_EVENT, TROOPA_PROJECT, TROOPA_REPO, TROOPA_TASK_ID, TROOPA_TASK, TROOPA_STATUS, TROOPA_AGENT, TROOPA_RUN_ID, TROOPA_BRANCH, TROOPA_WORKTREE, TROOPA_PLAN_ID, TROOPA_PLAN. Corren en segundo plano (límite de 2 minutos) dentro del worktree o del repo, y su salida va a ~/.local/share/troopa/hooks.log.

Extensiones

Cualquier programa llamado troopa-<nombre> en tu PATH se vuelve troopa <nombre>, como los subcomandos de git. Escríbelo en el lenguaje que quieras. Recibe los argumentos y TROOPA_BIN, TROOPA_CONFIG, TROOPA_DATA, TROOPA_DB y TROOPA_VERSION, y puede leer o cambiar los datos de Troopa con la CLI JSON.

#!/bin/sh
# ~/.local/bin/troopa-standup: tareas en revisión, como lista
"$TROOPA_BIN" task list --json --status review | jq -r '.data[] | "- " + .title'

troopa extensions lista las que encuentra. Los comandos propios de Troopa no se pueden reemplazar.

Daemon

troopa daemon es un proceso largo sin TUI. Cada pocos segundos mira los agentes en curso, termina una ejecución cuando el agente ha salido y arranca el siguiente paso de un plan con avance automático. El registro va a $XDG_DATA_HOME/troopa/daemon.log. Un archivo de pid evita que arranque un segundo daemon. La TUI sigue funcionando con o sin él.

troopa daemon
troopa daemon status
troopa daemon install
troopa daemon uninstall

install escribe una unidad de systemd de usuario en Linux (~/.config/systemd/user/troopa.service) y un agente launchd en macOS (~/Library/LaunchAgents/dev.troopa.plist), y lo activa. uninstall quita ese archivo. Windows aún no está soportado. status dice si está en marcha y qué ejecuciones vigila.
