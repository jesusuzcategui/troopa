Troopa documentation

Troopa is a terminal app to plan work, hand each task to an AI coding agent in its own git worktree, review the result and merge it. Everything lives in one SQLite file and one config.toml.

Getting started

  1. Install Troopa (install options) and at least one agent CLI: Claude Code, Codex, OpenCode, Cursor or Pi.
  2. Run troopa. The first run asks for language, theme, default agent, editor, terminal, merge strategy and the second brain folder. Run it again with troopa setup, or change anything later with S.
  3. Press n to create a project and point it to a git repository. If the folder does not exist, Troopa creates it with git init.
  4. Press enter to open its board, n to add a task, and move it to ready to launch its agent.

Press ? anywhere for the shortcuts of that screen and Ctrl+K for the command palette.

The whole flow, at a glance: a task joins a plan, gets its own worktree and agent, passes its checks and waits for your review in the TUI or on Telegram. Changes go back to the same agent; an approved step starts the next one, and the plan merges once or opens a PR. See it animated on the home page →

Projects and board

A project is a git repository. Its tasks move through inbox → backlog → ready → in-progress → review → done (plus blocked and pair-paused). Switch between board and list with v, fold statuses with z, open the task panel with tab.

enter on a task opens its run (the agent's answer, the diff and the log), even after it was merged; a task that never ran opens its form. e always edits the task. The side panel shows the whole task and its last run: scroll it with ctrl+d/ctrl+u or the mouse wheel; inside it (tab) j/k pick a field, ←/→ change it and PgUp/PgDn scroll. m, P and A change status, priority and agent from anywhere on the board.

Each task has a title, a description in Markdown, acceptance criteria (one per line), priority, agent, model, mode (yolo or pair), commit mode and type. Attach files with a and reference repo files with @path.

Clients (c on the project list) group projects; metrics (M) compare time, tokens and cost per agent and project.

Agents and runs

Moving a task to ready asks for confirmation and then:

  • creates a branch and a worktree under ~/.local/share/troopa/worktrees/<project>/,
  • writes TASK.md with the task, your profile, the project context and the rules,
  • starts the agent in the background. It keeps working if you close Troopa; Troopa picks it up when it opens again.

Yolo runs the agent alone and shows its live log. Pair opens the agent in a terminal next to you (TDD: red, green, refactor). When the agent ends, Troopa runs the project checks and moves the task to review or blocked.

If an agent stops before finishing (the computer turned off, for example), the run is marked blocked with a note; press x to send it back and continue.

Review and changes

The run screen has three tabs; switch with tab or 1 2 3:

  • Summary: what the agent answered in each round (it starts with “How to run”), your feedback and the checks. Scroll with j/k, PgUp/PgDn, G or the wheel; r folds a round and [/] pick one.
  • Changes: the diff. j/k move the line, n/p the file, enter comments the line, e/D edit or delete it, C lists the pending comments.
  • Log: the agent's raw log for the selected round.

x opens the request-changes screen with the agent's last answer on top (PgUp/PgDn scroll it): write what should change and press ctrl+s to send it, with your line comments, to the same agent in the same worktree. Each launch and each request is a round. The screen follows changes made from the daemon, MCP or Telegram while it is open. Runs that were merged, cleaned or discarded open read-only.

  • y approve: with commits = auto it commits, pushes and opens a PR when there is a remote.
  • g merge an approved branch into the base on this computer (squash or merge commit). A task approved without committing is committed first.
  • O push the branch and open a PR instead (needs a remote and gh).
  • U on the board pulls the base branch from its remote (fast-forward only), so the next task starts from fresh code.
  • c clean the worktree and keep the branch · d discard both.

Plans

A plan is an ordered list of tasks of a project that run one after the other. Press w on a board to see its plans.

  1. n creates a plan: title, goal, default agent and model, and auto-advance.
  2. Add the steps in order with a (enter adds, esc ends). Reorder with K/J. enter opens the step's run (esc comes back to the plan) and E edits the step like any task. v shows a long goal in full.
  3. s starts the plan: the first step that is not done launches.
  4. Each step goes through the normal review. Approving a step commits it on its branch, and the next step starts from that branch, so it builds on the work before it. With auto-advance on, it starts by itself; otherwise press s.
  5. When every step is done, open the plan and press g to merge the last branch (the whole plan) into the branch the plan started from, or O twice to push it and open a PR. After the PR is merged on the remote, g removes the step worktrees; U pulls the base branch.

Auto-approve (A, or in the plan form) lets a plan run alone: when a step's agent finishes and every check of troopa.toml passes, the step is approved and the next one starts. If a step fails, the plan stops there as blocked (the blocked hook can tell you), and after x fixes it the plan goes on. The merge at the end is always yours. Give the project real checks (tests, linters) before you turn it on: they are what decides. Without checks a step is never approved by itself; it waits in review with a note saying so.

p pauses (the running step finishes, the next one waits), t toggles auto-advance. A step that is blocked stops the plan until you fix it with x. Steps never merge on their own.

Profiles

A profile tells the agents who they work for. It is not only for developers: create one per profession you have (developer, chef, designer, accountant, writer, HR…). Each profile has a name, a profession, an “about” text and standing instructions.

Open them from Settings (S → Profiles) or the palette. * marks the default profile; a project can pick another one in its form (←/→ on Profile). The profile is written into every TASK.md under “Who you work for”:

## Who you work for

You are working for Ana (Chef). Use the words, standards and tools of that profession.

Runs a bakery with two stores.

Their standing instructions:

Metric units. Recipes for 12 portions.

Accounts

Accounts let agents run with a different login per project, for example a company subscription for a client and your personal one for everything else. Each account keeps its own login folder for every agent, so signing in to one never touches the other.

# ~/.config/troopa/config.toml
default_account = ""          # "" = the agents' normal login

[accounts.acme]
# dir = "~/.troopa-accounts/acme"   # optional; default ~/.config/troopa/accounts/acme
# env = { ANTHROPIC_API_KEY = "…" }  # optional extra variables

Sign each agent in once, then pick the account in the project form (Account):

troopa login acme claude
troopa login acme codex

Troopa sets CLAUDE_CONFIG_DIR (Claude Code), CODEX_HOME (Codex), XDG_DATA_HOME (OpenCode) and PI_CODING_AGENT_DIR (Pi) to the account folder. If your agent reads another variable, set it in env.

Second brain

A Markdown folder (Obsidian-friendly) that Troopa keeps up to date: inbox.md, today.md, projects/INDEX.md and, per project, project.md, tasks/ and guides/ (how to run what was merged). The agent gets the project note as context. Browse it with B, search with /, add to the inbox with i. Set brain_git = true for local commits.

Graph

Press G in the brain to see it as a graph, drawn in the terminal with braille dots. The local view puts the open note in the middle with its links around it: ←/→ pick a note, enter centers on it (and opens it when it is already the center), 1/2 show one or two rings of links. v switches to the whole brain, laid out by a force simulation: arrows move to the nearest note, +/- or the mouse wheel zoom, 0 fits everything. Tasks and guides are tied to their project even without a written link. A click selects a note; a second click opens it.

Hooks

Hooks are shell commands that run on events: task_created, launch, review, blocked, approve, merge, discard, plan_start, plan_done. Put them in config.toml (every project) or in the project's troopa.toml. An event takes one command or a list.

[hooks]
review = "notify-send 'Troopa' \"$TROOPA_TASK is ready for review\""
approve = ["./scripts/deploy-staging.sh", "curl -s -X POST $SLACK_URL -d @-"]

Each hook gets the event as JSON on stdin and in variables: TROOPA_EVENT, TROOPA_PROJECT, TROOPA_REPO, TROOPA_TASK_ID, TROOPA_TASK, TROOPA_STATUS, TROOPA_AGENT, TROOPA_RUN_ID, TROOPA_BRANCH, TROOPA_WORKTREE, TROOPA_PLAN_ID, TROOPA_PLAN. Hooks run in the background (2-minute limit) inside the worktree or the repo, and their output goes to ~/.local/share/troopa/hooks.log.

Recipe: Telegram alerts

Get a message on your phone when a step is ready for review, approves itself, gets blocked or a plan ends: with the agent's summary, the checks, the time, the tokens and the cost. troopa notify telegram builds it from the hook event and the run.

  1. In Telegram, talk to @BotFather, send /newbot and keep the token it gives you.
  2. Send any message to your new bot, then get your chat id: 
    curl -s "https://api.telegram.org/bot<TOKEN>/getUpdates" | grep -o '"chat":{"id":-\?[0-9]*'
  3. Add the bot and the hooks to ~/.config/troopa/config.toml: 
    [telegram]
token   = "<TOKEN>"
chat_id = "<CHAT_ID>"
actions = true            # answer from Telegram (needs troopa daemon)

[hooks]
review    = "troopa notify telegram"
blocked   = "troopa notify telegram"
approve   = "troopa notify telegram"
plan_done = "troopa notify telegram"
    --token/--chat flags or TROOPA_TELEGRAM_TOKEN/TROOPA_TELEGRAM_CHAT override [telegram]. If troopa is not on the PATH of the process that runs the hook, write its full path.
  4. Try it: troopa notify telegram --test --token … --chat … sends the latest run as a sample; --dry-run prints the message instead.

Blocked messages show the failing check with its last lines; approve messages name the next step of the plan; with auto-approve on, a step sends one message (approved), not two. Messages follow the Troopa language.

Answer from Telegram

With actions = true and troopa daemon running (troopa daemon install keeps it up), each alert comes with buttons, and the bot takes commands. It polls Telegram, so no public server or open port is needed, and it obeys chat_id only: messages from anyone else are ignored.

  • ✅ Approve: approves the run; in a plan, the next step starts.
  • ✏️ Request changes: the bot asks you to reply with what to change, and sends your reply to the same agent (like x).
  • 📄 Diff and 📜 Log: the patch (as a file when it is long) and the last lines of the agent.
  • /status, /plans, /plan 3, /run 3 (start or resume), /pause 3, /task app Dark mode toggle, /tasks, /launch 7, /chat, /end, /log 12, /diff 12, /help.

You don't need to type them. The bot fills Telegram's menu with its commands, and /start pins a keyboard under the text box: 📊 Status, 🗺 Plans, 📋 Tasks, ➕ New task, 📁 New project, 💬 Chat, ❓ Help. From there everything is buttons that redraw the same message:

  • Plans lists each plan with its progress; tap one to see its steps, with ▶️ Start or ⏸ Pause, and approve, request changes or open the diff of the step waiting for review.
  • Status shows what is running, waiting or blocked, with the same buttons for each run.
  • New task asks for the project with a button, then for the title as a reply; the task lands in that project's backlog with a ▶️ button per installed agent.
  • New project (or /project) asks for a name, or a git URL to clone, then for the folder with a button (the ones your projects already live in). A name starts a fresh repository; a URL is cloned. Only the owner can create projects.
  • Tasks (or /tasks) has a tab per status: pending, running, review, blocked and done. Open a task to launch it with the agent you pick, read its summary, approve it, request changes, leave comments (they wait and go to the agent together with your next request for changes), or, once approved, merge it, open a PR, or pull the base branch with separate buttons. A finished plan merges or opens its PR from its own screen.

Chat (or /chat) opens a conversation with any installed agent: pick the agent, then the project it works in (a project called Conversar comes first, so keep one just for chatting). Every message you write goes to the agent with the whole conversation so far, and its answer comes back to the chat. Nothing becomes a task, a worktree or a run; the transcript is kept in Troopa's data folder. 🔚 End conversation (or /end) closes it.

Share the bot

Someone else can use the same bot from their own Telegram, with their projects only. They send /start to the bot, which answers with their chat id; add them to config.toml and restart the daemon:

[[telegram.users]]
name = "Ana"
chat_id = "123456789"
projects = ["crochet"]   # slugs or names
agent = "codex"          # for the tasks they send; optional

They see, launch, approve and merge in their projects only, get the alerts of those projects (you still get every alert), and never see the rest.

Photos. A photo with a caption becomes a task in their project, with the photo attached and the caption as the request, and it launches right away. If another agent is working, it waits in a queue and starts when that one finishes; they get a message when it does. Codex receives the photo with --image; other agents read it from the worktree. The images the agent creates or changes come back with the review alert, next to Approve and Changes, and a task's 🖼 Images button sends them again. Inside a conversation a photo goes to the agent with the message, and the pictures it makes come back in the chat.

Merge and PR always ask first. The TUI stays in sync: whatever you do from Telegram shows up on the board within a couple of seconds. Use a bot of its own for Troopa: two programs cannot read the same bot's messages at once.

Recipe: Android with Termux

Run Troopa and an agent on your phone. Android cannot run the Linux binaries of Troopa or OpenCode directly, so they run inside a Debian installed in Termux with proot-distro (no root needed). Your projects live in one folder shared by Termux, Debian and your Android editor.

  1. Install Termux from F-Droid or GitHub (the Play Store build is outdated). Open it and install the tools: 
    pkg update && pkg upgrade
pkg install proot-distro
termux-setup-storage
  2. Install Debian, create the projects folder and an alias that enters Debian with that folder mounted: 
    proot-distro install debian
mkdir -p ~/proyectos
echo "alias deb='proot-distro login debian --bind \$HOME/proyectos:/root/proyectos'" >> ~/.bashrc
source ~/.bashrc
deb
    From now on, deb takes you into Debian. Everything below runs there.
  3. Inside Debian, install git, tmux and micro, a terminal editor with the usual shortcuts (Ctrl+S save, Ctrl+Q quit), and set your git identity: 
    apt update && apt install -y curl git ca-certificates tmux micro
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
echo 'export EDITOR=micro' >> ~/.bashrc
  4. Install OpenCode and connect a provider (inside OpenCode, /connect and follow the prompts): 
    curl -fsSL https://opencode.ai/install | bash
echo 'export PATH="$HOME/.opencode/bin:$PATH"' >> ~/.bashrc
source ~/.bashrc
opencode
    Other agents install the same way inside Debian, for example Claude Code or Codex with Node: apt install -y nodejs npm, then npm install -g @anthropic-ai/claude-code or npm install -g @openai/codex. Sign in to each one once before using it from Troopa.
  5. Install Troopa: 
    curl -fsSL https://jesusuzcategui.github.io/troopa/install.sh | sh
echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.bashrc
source ~/.bashrc
troopa
    In the first-run setup pick OpenCode (or your agent) as the default agent and micro as the editor. Create your projects under /root/proyectos.
  6. Use yolo mode for tasks on the phone: the agent works alone and you review the result in Troopa. Set it as the default mode in Settings (S).

Pair mode and a second terminal. Pair mode opens the agent in another terminal, and there is no desktop terminal on Android. Run Troopa inside tmux and pair tasks open the agent in a split next to it (Ctrl+B then an arrow key moves between panes):

tmux
troopa

If you prefer not to use tmux, Termux itself has sessions: swipe from the left edge, tap New session, run deb again and start the agent there by hand. Tools like Termux:X11 can run a desktop terminal, but they cost far more battery and memory for little gain on a phone.

Edit from Android. Install Acode (Play Store or F-Droid), choose Open folder, pick Termux in the Android file picker and open proyectos. What you save there is what Debian, Troopa and the agent see.

Keep agents running. Android stops background apps. Pull down the Termux notification and tap Acquire wakelock (or run termux-wake-lock in Termux), and turn off battery optimization for Termux. With the Telegram bot you can follow the agents without keeping Termux open on screen.

Extensions

Any program named troopa-<name> on your PATH becomes troopa <name>, like git subcommands. Write it in any language. It receives the arguments and TROOPA_BIN, TROOPA_CONFIG, TROOPA_DATA, TROOPA_DB and TROOPA_VERSION, and can read or change Troopa's data through the JSON CLI.

#!/bin/sh
# ~/.local/bin/troopa-standup: tasks in review, as a list
"$TROOPA_BIN" task list --json --status review | jq -r '.data[] | "- " + .title'

troopa extensions lists the ones it finds. Built-in commands cannot be replaced.

MCP and daemon

Keep plans moving with troopa daemon, then register the MCP server with your client. Merge of a plan or a task stays in the TUI (g); MCP can review, not ship.

Setup

troopa daemon install
troopa mcp install claude    # or codex, opencode, cursor

troopa daemon is a long-running process without the TUI. Every few seconds it looks at running agents, finishes a run when the agent has exited, and starts the next step of a plan that has auto-advance. Logs go to $XDG_DATA_HOME/troopa/daemon.log. A pid file keeps a second daemon from starting. The TUI keeps working with or without it.

troopa daemon
troopa daemon status
troopa daemon install
troopa daemon uninstall

daemon install writes a systemd user unit on Linux (~/.config/systemd/user/troopa.service) and a launchd agent on macOS (~/Library/LaunchAgents/dev.troopa.plist), then enables it. uninstall removes that file. Windows is not supported yet. status prints whether it is running and the runs it watches.

troopa mcp is an MCP server over stdio in the same binary. troopa mcp install registers it: Claude Code runs claude mcp add --scope user troopa -- /full/path/troopa mcp; Codex, OpenCode and Cursor get a TOML or JSON snippet in their config. It writes the full path of the binary, so the client finds it even when troopa is not on its PATH. If the client is not installed, Troopa prints that snippet instead. For the Claude desktop app, add "troopa": {"command": "/full/path/troopa", "args": ["mcp"]} under mcpServers in Settings → Developer → Edit Config.

Tools

Tools return JSON in the same shapes as the CLI.

Read: projects_list, project_show, tasks_list (filters: project, status, plan), task_show, plans_list, plan_show (steps with status and latest run), run_show (summary, checks, state, branch, rounds), run_diff (files and size-limited patch text), run_log (log tail), brain_search, brain_read (paths inside the brain only), profiles_list.

Write tools fire the same hooks as the TUI: task_create, task_update, task_move, plan_create (title, goal, agent, model, auto, and steps in one call), plan_add_step, plan_update. plan_start and plan_pause go through the engine. If no daemon is running, start watches from the MCP process and the result says that troopa daemon keeps plans moving. run_wait (run_id or plan_id, timeout_seconds at most 600) blocks until the run leaves running or the plan step changes, and returns state, summary and checks. On timeout the state is still running.

Review loop

review_request_changes (run_id, feedback, comments with path, line, side, body) matches x in the TUI: a new round, notes in CHANGES.md, same agent continues. review_approve needs [mcp] allow_approve = true in config.toml (off by default; Settings has the toggle). There is no merge tool: merging is a local decision on g, after you have seen the branch.

JSON CLI

Every resource has a versioned JSON command (schema_version 1) that uses the same store as the TUI:

troopa project list --json
troopa task create --json --project 1 --title "Add search" --agent codex
troopa plan create --json --project 1 --title "Checkout" --agent claude
troopa plan add-step --json --id 1 --title "Cart page"
troopa profile create --json --name Ana --profession Chef
troopa run rounds --json --id 3
troopa brain sync --json

Resources: project, client, task, run, plan, profile, brain. The full reference is in docs/cli-json.md.

Documentación de Troopa

Troopa es una app de terminal para planear el trabajo, darle cada tarea a un agente de IA en su propio worktree de git, revisar el resultado y hacer merge. Todo vive en un archivo SQLite y un config.toml.

Primeros pasos

  1. Instala Troopa (opciones de instalación) y al menos un agente: Claude Code, Codex, OpenCode, Cursor o Pi.
  2. Ejecuta troopa. El primer arranque pregunta idioma, tema, agente por defecto, editor, terminal, estrategia de merge y la carpeta del segundo cerebro. Repítelo con troopa setup o cambia todo después con S.
  3. Pulsa n para crear un proyecto y apúntalo a un repositorio git. Si la carpeta no existe, Troopa la crea con git init.
  4. Pulsa enter para abrir su tablero, n para agregar una tarea y muévela a ready para lanzar su agente.

Pulsa ? en cualquier pantalla para ver sus atajos y Ctrl+K para la paleta de comandos.

El flujo completo, de un vistazo: una tarea entra a un plan, recibe su propio worktree y su agente, pasa sus checks y espera tu revisión en la TUI o en Telegram. Los cambios vuelven al mismo agente; un paso aprobado arranca el siguiente, y el plan hace un solo merge o abre un PR. Míralo animado en la página de inicio →

Proyectos y tablero

Un proyecto es un repositorio git. Sus tareas pasan por inbox → backlog → ready → in-progress → review → done (más blocked y pair-paused). Cambia entre tablero y lista con v, pliega estados con z y abre el panel de la tarea con tab.

enter en una tarea abre su ejecución (la respuesta del agente, el diff y el log), incluso después del merge; una tarea que nunca corrió abre su formulario. e siempre edita la tarea. El panel lateral muestra la tarea completa y su última ejecución: desplázalo con ctrl+d/ctrl+u o la rueda del mouse; dentro de él (tab) j/k eligen un campo, ←/→ lo cambian y RePág/AvPág desplazan. m, P y A cambian estado, prioridad y agente desde cualquier parte del tablero.

Cada tarea tiene título, descripción en Markdown, criterios de aceptación (uno por línea), prioridad, agente, modelo, modo (yolo o pair), modo de commits y tipo. Adjunta archivos con a y referencia archivos del repo con @ruta.

Los clientes (c en la lista de proyectos) agrupan proyectos; las métricas (M) comparan tiempo, tokens y costo por agente y por proyecto.

Agentes y ejecuciones

Al mover una tarea a ready, Troopa pide confirmación y luego:

  • crea una rama y un worktree en ~/.local/share/troopa/worktrees/<proyecto>/,
  • escribe TASK.md con la tarea, tu perfil, el contexto del proyecto y las reglas,
  • arranca el agente en segundo plano. Sigue trabajando aunque cierres Troopa; Troopa lo retoma al abrirse.

Yolo ejecuta el agente solo y muestra su log en vivo. Pair abre el agente en una terminal a tu lado (TDD: rojo, verde, refactor). Cuando el agente termina, Troopa corre los checks del proyecto y mueve la tarea a review o blocked.

Si un agente se detiene antes de terminar (por ejemplo, se apagó el equipo), la ejecución queda en blocked con una nota; pulsa x para devolvérsela y continuar.

Revisión y cambios

La pantalla de una ejecución tiene tres pestañas; cambia con tab o 1 2 3:

  • Resumen: lo que respondió el agente en cada ronda (empieza con “How to run”), tus comentarios y los checks. Desplázate con j/k, RePág/AvPág, G o la rueda; r pliega una ronda y [/] eligen una.
  • Cambios: el diff. j/k mueven la línea, n/p el archivo, enter comenta la línea, e/D la editan o borran, C lista los comentarios pendientes.
  • Log: el log del agente de la ronda elegida.

x abre la pantalla de pedir cambios con la última respuesta del agente arriba (RePág/AvPág la desplazan): escribe qué debe cambiar y pulsa ctrl+s para mandarlo, con tus comentarios de línea, al mismo agente en el mismo worktree. Cada lanzamiento y cada pedido es una ronda. La pantalla sigue los cambios hechos desde el daemon, el MCP o Telegram mientras está abierta. Las ejecuciones ya mergeadas, limpiadas o descartadas se abren solo para leer.

  • y aprobar: con commits = auto hace commit, push y abre un PR si hay remoto.
  • g merge de una rama aprobada en la base, en esta computadora (squash o merge commit). Si la tarea se aprobó sin commit, primero se hace el commit.
  • O en vez del merge, sube la rama y abre un PR (necesita remoto y gh).
  • U en el tablero hace pull de la rama base desde el remoto (solo fast-forward), para que la siguiente tarea arranque con el código al día.
  • c limpiar el worktree y conservar la rama · d descartar ambos.

Planes

Un plan es una lista ordenada de tareas de un proyecto que se ejecutan una tras otra. Pulsa w en un tablero para ver sus planes.

  1. n crea un plan: título, objetivo, agente y modelo por defecto, y avance automático.
  2. Agrega los pasos en orden con a (enter agrega, esc termina). Reordena con K/J. enter abre la ejecución del paso (esc vuelve al plan) y E edita el paso como cualquier tarea. v muestra completo un objetivo largo.
  3. s inicia el plan: se lanza el primer paso que no esté terminado.
  4. Cada paso pasa por la revisión normal. Al aprobar un paso se hace commit en su rama y el siguiente arranca desde esa rama, así construye sobre el trabajo anterior. Con avance automático arranca solo; si no, pulsa s.
  5. Cuando todos los pasos están listos, abre el plan y pulsa g para mergear la última rama (el plan completo) en la rama desde la que empezó el plan, o O dos veces para subirla y abrir un PR. Cuando el PR se fusiona en el remoto, g elimina los worktrees de los pasos; U hace pull de la rama base.

La aprobación automática (A, o en el formulario del plan) deja que el plan corra solo: cuando el agente de un paso termina y todos los checks de troopa.toml pasan, el paso se aprueba y arranca el siguiente. Si un paso falla, el plan se detiene ahí en blocked (el hook blocked te puede avisar), y cuando lo arreglas con x el plan sigue. El merge final siempre es tuyo. Dale al proyecto checks de verdad (tests, linters) antes de activarla: son los que deciden. Sin checks, ningún paso se aprueba solo; queda en revisión con una nota que lo explica.

p pausa (el paso en curso termina y el siguiente espera), t activa o desactiva el avance automático. Un paso bloqueado detiene el plan hasta que lo arregles con x. Los pasos nunca hacen merge por separado.

Perfiles

Un perfil le dice a los agentes para quién trabajan. No es solo para programadores: crea uno por cada profesión que tengas (programador, chef, diseñador, contador, escritor, recursos humanos…). Cada perfil tiene nombre, profesión, un texto “sobre ti” e instrucciones fijas.

Ábrelos desde Configuración (S → Perfiles) o la paleta. * marca el perfil por defecto; un proyecto puede elegir otro en su formulario (←/→ en Perfil). El perfil se escribe en cada TASK.md bajo “Who you work for”:

## Who you work for

You are working for Ana (Chef). Use the words, standards and tools of that profession.

Runs a bakery with two stores.

Their standing instructions:

Metric units. Recipes for 12 portions.

Cuentas

Las cuentas permiten que los agentes usen un login distinto por proyecto, por ejemplo la suscripción de una empresa para un cliente y la tuya personal para lo demás. Cada cuenta guarda su propia carpeta de login por agente, así iniciar sesión en una nunca toca la otra.

# ~/.config/troopa/config.toml
default_account = ""          # "" = el login normal de los agentes

[accounts.acme]
# dir = "~/.troopa-accounts/acme"   # opcional; por defecto ~/.config/troopa/accounts/acme
# env = { ANTHROPIC_API_KEY = "…" }  # variables extra opcionales

Inicia sesión una vez con cada agente y elige la cuenta en el formulario del proyecto (Cuenta):

troopa login acme claude
troopa login acme codex

Troopa apunta CLAUDE_CONFIG_DIR (Claude Code), CODEX_HOME (Codex), XDG_DATA_HOME (OpenCode) y PI_CODING_AGENT_DIR (Pi) a la carpeta de la cuenta. Si tu agente usa otra variable, ponla en env.

Segundo cerebro

Una carpeta Markdown (compatible con Obsidian) que Troopa mantiene al día: inbox.md, today.md, projects/INDEX.md y, por proyecto, project.md, tasks/ y guides/ (cómo correr lo que se mergeó). El agente recibe la nota del proyecto como contexto. Recórrelo con B, busca con / y agrega al inbox con i. Con brain_git = true hace commits locales.

Grafo

Pulsa G en el cerebro para verlo como grafo, dibujado en la terminal con puntos braille. La vista local pone la nota abierta en el centro con sus enlaces alrededor: ←/→ eligen una nota, enter la centra (y la abre si ya es el centro), 1/2 muestran uno o dos anillos de enlaces. v cambia a todo el cerebro, acomodado con una simulación de fuerzas: las flechas van a la nota más cercana, +/- o la rueda del ratón hacen zoom y 0 ajusta todo. Las tareas y guías quedan unidas a su proyecto aunque no tengan un enlace escrito. Un clic elige una nota; un segundo clic la abre.

Hooks

Los hooks son comandos de shell que corren en eventos: task_created, launch, review, blocked, approve, merge, discard, plan_start, plan_done. Ponlos en config.toml (todos los proyectos) o en el troopa.toml del proyecto. Un evento acepta un comando o una lista.

[hooks]
review = "notify-send 'Troopa' \"$TROOPA_TASK está lista para revisar\""
approve = ["./scripts/deploy-staging.sh", "curl -s -X POST $SLACK_URL -d @-"]

Cada hook recibe el evento como JSON por stdin y en variables: TROOPA_EVENT, TROOPA_PROJECT, TROOPA_REPO, TROOPA_TASK_ID, TROOPA_TASK, TROOPA_STATUS, TROOPA_AGENT, TROOPA_RUN_ID, TROOPA_BRANCH, TROOPA_WORKTREE, TROOPA_PLAN_ID, TROOPA_PLAN. Corren en segundo plano (límite de 2 minutos) dentro del worktree o del repo, y su salida va a ~/.local/share/troopa/hooks.log.

Receta: avisos por Telegram

Recibe un mensaje en el celular cuando un paso está listo para revisar, se aprueba solo, se bloquea o termina un plan: con el resumen del agente, los checks, el tiempo, los tokens y el costo. troopa notify telegram lo arma con el evento del hook y la ejecución.

  1. En Telegram, habla con @BotFather, envía /newbot y guarda el token que te da.
  2. Mándale cualquier mensaje a tu bot y saca tu chat id: 
    curl -s "https://api.telegram.org/bot<TOKEN>/getUpdates" | grep -o '"chat":{"id":-\?[0-9]*'
  3. Agrega el bot y los hooks a ~/.config/troopa/config.toml: 
    [telegram]
token   = "<TOKEN>"
chat_id = "<CHAT_ID>"
actions = true            # responder desde Telegram (requiere troopa daemon)

[hooks]
review    = "troopa notify telegram"
blocked   = "troopa notify telegram"
approve   = "troopa notify telegram"
plan_done = "troopa notify telegram"
    Los flags --token/--chat o TROOPA_TELEGRAM_TOKEN/TROOPA_TELEGRAM_CHAT tienen prioridad sobre [telegram]. Si troopa no está en el PATH del proceso que corre el hook, escribe su ruta completa.
  4. Pruébalo: troopa notify telegram --test --token … --chat … envía la última ejecución como ejemplo; --dry-run imprime el mensaje en vez de enviarlo.

Así se ve un mensaje (el resumen se abre con un toque):

✅ Listo para revisar

📁 Solar system
🗺 Moons · paso 2 de 5
📝 Add the outer planets and moons
🤖 Cursor  ·  ⏱ 12m 34s  ·  🔤 120.5k in · 8.2k out  ·  💰 $0.42
🌿 feature/add-the-outer-planets-and-moons

Checks
✅ go vet ./...
✅ go test ./...

Lo que dice el agente
┃ What changed
┃ • Added Jupiter and Saturn, and moons that orbit their planet
┃ How to run
┃ npm start

👉 En Troopa: y aprueba, x lo devuelve con tus comentarios.

Los mensajes de bloqueo muestran el check que falló con sus últimas líneas; los de aprobación nombran el siguiente paso del plan; con la aprobación automática, cada paso manda un solo mensaje (aprobado), no dos. Los mensajes siguen el idioma de Troopa.

Responder desde Telegram

Con actions = true y troopa daemon corriendo (troopa daemon install lo deja siempre activo), cada aviso trae botones y el bot acepta comandos. Pregunta a Telegram por mensajes nuevos, así que no necesita servidor público ni abrir puertos, y solo obedece a chat_id: ignora los mensajes de cualquier otra persona.

  • ✅ Aprobar: aprueba la ejecución; en un plan, arranca el siguiente paso.
  • ✏️ Pedir cambios: el bot te pide que respondas con lo que hay que cambiar y le manda tu respuesta al mismo agente (como x).
  • 📄 Diff y 📜 Log: el parche (como archivo si es largo) y las últimas líneas del agente.
  • /status, /plans, /plan 3, /run 3 (iniciar o retomar), /pause 3, /task app Modo oscuro, /tareas, /lanzar 7, /conversar, /cerrar, /log 12, /diff 12, /help.

No hace falta escribirlos. El bot llena el menú de Telegram con sus comandos, y /start deja fijo un teclado bajo la caja de texto: 📊 Estado, 🗺 Planes, 📋 Tareas, ➕ Nueva tarea, 📁 Nuevo proyecto, 💬 Conversar, ❓ Ayuda. De ahí en adelante todo son botones que redibujan el mismo mensaje:

  • Planes lista cada plan con su avance; toca uno para ver sus pasos, con ▶️ Iniciar o ⏸ Pausar, y aprobar, pedir cambios o abrir el diff del paso que espera revisión.
  • Estado muestra lo que está corriendo, esperando o bloqueado, con los mismos botones en cada ejecución.
  • Nueva tarea te pide el proyecto con un botón y luego el título como respuesta; la tarea cae en el backlog de ese proyecto con un botón ▶️ por cada agente instalado.
  • Nuevo proyecto (o /proyecto) pide un nombre, o una URL de git para clonar, y luego la carpeta con un botón (las carpetas donde ya viven tus proyectos). Un nombre crea un repositorio nuevo; una URL se clona. Solo el dueño puede crear proyectos.
  • Tareas (o /tareas) tiene una pestaña por estado: pendientes, en curso, revisión, bloqueadas y hechas. Abre una tarea para lanzarla con el agente que elijas, leer su resumen, aprobarla, pedir cambios, dejar comentarios (esperan y van al agente junto con tu siguiente pedido de cambios) o, ya aprobada, hacer merge, abrir un PR o hacer pull de la rama base, cada uno con su botón. Un plan terminado hace merge o abre su PR desde su propia pantalla.

Conversar (o /conversar) abre una conversación con cualquier agente instalado: eliges el agente y luego el proyecto donde trabaja (un proyecto llamado Conversar sale primero, así que puedes tener uno solo para esto). Cada mensaje que escribes le llega al agente con toda la conversación, y su respuesta vuelve al chat. Nada se vuelve tarea, worktree ni ejecución; la transcripción queda en la carpeta de datos de Troopa. 🔚 Cerrar conversación (o /cerrar) la termina.

Compartir el bot

Otra persona puede usar el mismo bot desde su Telegram, solo con sus proyectos. Le manda /start al bot, que le responde con el id de su chat; agrégala en config.toml y reinicia el daemon:

[[telegram.users]]
name = "Ana"
chat_id = "123456789"
projects = ["crochet"]   # slugs o nombres
agent = "codex"          # para las tareas que envía; opcional

Ve, lanza, aprueba y hace merge solo en sus proyectos, recibe los avisos de esos proyectos (tú sigues recibiendo todos) y nunca ve lo demás.

Fotos. Una foto con texto se vuelve una tarea en su proyecto, con la foto adjunta y el texto como pedido, y arranca de una vez. Si otro agente está trabajando, espera en una cola y arranca cuando ese termine; le llega un mensaje cuando pasa. Codex recibe la foto con --image; los demás agentes la leen del worktree. Las imágenes que el agente crea o cambia llegan con el aviso de revisión, junto a Aprobar y Cambios, y el botón 🖼 Imágenes de la tarea las vuelve a enviar. Dentro de una conversación, la foto le llega al agente con el mensaje y las imágenes que hace vuelven al chat.

El merge y el PR siempre piden confirmación. La TUI se mantiene al día: lo que hagas desde Telegram aparece en el tablero en un par de segundos. Usa un bot solo para Troopa: dos programas no pueden leer los mensajes del mismo bot a la vez.

Receta: Android con Termux

Corre Troopa y un agente en el celular. Android no puede ejecutar directo los binarios de Linux de Troopa ni de OpenCode, así que corren dentro de un Debian instalado en Termux con proot-distro (no hace falta root). Tus proyectos viven en una carpeta compartida entre Termux, Debian y tu editor de Android.

  1. Instala Termux desde F-Droid o GitHub (la versión de Play Store está desactualizada). Ábrelo e instala las herramientas: 
    pkg update && pkg upgrade
pkg install proot-distro
termux-setup-storage
  2. Instala Debian, crea la carpeta de proyectos y un alias que entra a Debian con esa carpeta montada: 
    proot-distro install debian
mkdir -p ~/proyectos
echo "alias deb='proot-distro login debian --bind \$HOME/proyectos:/root/proyectos'" >> ~/.bashrc
source ~/.bashrc
deb
    Desde ahora, deb te lleva a Debian. Todo lo que sigue se corre ahí.
  3. Dentro de Debian, instala git, tmux y micro, un editor de terminal con los atajos de siempre (Ctrl+S guardar, Ctrl+Q salir), y configura tu identidad de git: 
    apt update && apt install -y curl git ca-certificates tmux micro
git config --global user.name "Tu Nombre"
git config --global user.email "tu@correo.com"
echo 'export EDITOR=micro' >> ~/.bashrc
  4. Instala OpenCode y conecta un proveedor (dentro de OpenCode, /connect y sigue los pasos): 
    curl -fsSL https://opencode.ai/install | bash
echo 'export PATH="$HOME/.opencode/bin:$PATH"' >> ~/.bashrc
source ~/.bashrc
opencode
    Los otros agentes se instalan igual dentro de Debian, por ejemplo Claude Code o Codex con Node: apt install -y nodejs npm y luego npm install -g @anthropic-ai/claude-code o npm install -g @openai/codex. Inicia sesión en cada uno una vez antes de usarlo desde Troopa.
  5. Instala Troopa: 
    curl -fsSL https://jesusuzcategui.github.io/troopa/install.sh | sh
echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.bashrc
source ~/.bashrc
troopa
    En la configuración inicial elige OpenCode (o tu agente) como agente por defecto y micro como editor. Crea tus proyectos dentro de /root/proyectos.
  6. Usa el modo yolo para las tareas en el celular: el agente trabaja solo y tú revisas el resultado en Troopa. Déjalo como modo por defecto en Ajustes (S).

Modo pair y una segunda terminal. El modo pair abre al agente en otra terminal, y en Android no hay terminales de escritorio. Corre Troopa dentro de tmux y las tareas pair abren al agente en una división al lado (Ctrl+B y una flecha te mueven entre paneles):

tmux
troopa

Si prefieres no usar tmux, Termux tiene sesiones propias: desliza desde el borde izquierdo, toca New session, corre deb otra vez y arranca ahí el agente a mano. Herramientas como Termux:X11 pueden correr una terminal de escritorio, pero gastan mucha más batería y memoria para poca ganancia en un celular.

Editar desde Android. Instala Acode (Play Store o F-Droid), elige Abrir carpeta, escoge Termux en el selector de archivos de Android y abre proyectos. Lo que guardes ahí es lo mismo que ven Debian, Troopa y el agente.

Que los agentes sigan corriendo. Android detiene las apps en segundo plano. Despliega la notificación de Termux y toca Acquire wakelock (o corre termux-wake-lock en Termux), y desactiva la optimización de batería para Termux. Con el bot de Telegram sigues a los agentes sin tener Termux abierto en pantalla.

Extensiones

Cualquier programa llamado troopa-<nombre> en tu PATH se vuelve troopa <nombre>, como los subcomandos de git. Escríbelo en el lenguaje que quieras. Recibe los argumentos y TROOPA_BIN, TROOPA_CONFIG, TROOPA_DATA, TROOPA_DB y TROOPA_VERSION, y puede leer o cambiar los datos de Troopa con la CLI JSON.

#!/bin/sh
# ~/.local/bin/troopa-standup: tareas en revisión, como lista
"$TROOPA_BIN" task list --json --status review | jq -r '.data[] | "- " + .title'

troopa extensions lista las que encuentra. Los comandos propios de Troopa no se pueden reemplazar.

MCP y daemon

Mantén los planes en marcha con troopa daemon y registra el servidor MCP en tu cliente. El merge de un plan o una tarea se queda en la TUI (g); MCP puede revisar, no publicar.

Configuración

troopa daemon install
troopa mcp install claude    # o codex, opencode, cursor

troopa daemon es un proceso largo sin TUI. Cada pocos segundos mira los agentes en curso, termina una ejecución cuando el agente ha salido y arranca el siguiente paso de un plan con avance automático. El registro va a $XDG_DATA_HOME/troopa/daemon.log. Un archivo de pid evita que arranque un segundo daemon. La TUI sigue funcionando con o sin él.

troopa daemon
troopa daemon status
troopa daemon install
troopa daemon uninstall

daemon install escribe una unidad de systemd de usuario en Linux (~/.config/systemd/user/troopa.service) y un agente launchd en macOS (~/Library/LaunchAgents/dev.troopa.plist), y lo activa. uninstall quita ese archivo. Windows aún no está soportado. status dice si está en marcha y qué ejecuciones vigila.

troopa mcp es un servidor MCP por stdio en el mismo binario. troopa mcp install lo registra: Claude Code corre claude mcp add --scope user troopa -- /ruta/completa/troopa mcp; Codex, OpenCode y Cursor reciben un fragmento TOML o JSON en su config. Escribe la ruta completa del binario, así el cliente lo encuentra aunque troopa no esté en su PATH. Si el cliente no está instalado, Troopa imprime ese fragmento. Para la app de escritorio de Claude, agrega "troopa": {"command": "/ruta/completa/troopa", "args": ["mcp"]} en mcpServers desde Settings → Developer → Edit Config.

Herramientas

Las herramientas devuelven JSON con las mismas formas que la CLI.

Lectura: projects_list, project_show, tasks_list (filtros: project, status, plan), task_show, plans_list, plan_show (pasos con estado y última ejecución), run_show (resumen, checks, estado, rama, rondas), run_diff (archivos y parche con límite de tamaño), run_log (cola del log), brain_search, brain_read (solo rutas dentro del cerebro), profiles_list.

Las herramientas de escritura disparan los mismos hooks que la TUI: task_create, task_update, task_move, plan_create (título, objetivo, agente, modelo, auto y pasos en una llamada), plan_add_step, plan_update. plan_start y plan_pause pasan por el motor. Si no hay daemon, el arranque vigila desde el proceso MCP y el resultado dice que troopa daemon sigue moviendo los planes. run_wait (run_id o plan_id, timeout_seconds como máximo 600) espera a que la ejecución deje de estar en curso o cambie el paso del plan, y devuelve estado, resumen y checks. Si se agota el tiempo, el estado sigue running.

Bucle de revisión

review_request_changes (run_id, feedback, comments con path, line, side, body) es lo mismo que x en la TUI: una ronda nueva, notas en CHANGES.md y el mismo agente sigue. review_approve exige [mcp] allow_approve = true en config.toml (desactivado por defecto; Configuración tiene el interruptor). No hay herramienta de merge: el merge es una decisión local con g, después de ver la rama.

CLI JSON

Cada recurso tiene un comando JSON versionado (schema_version 1) que usa el mismo almacenamiento que la TUI:

troopa project list --json
troopa task create --json --project 1 --title "Agregar búsqueda" --agent codex
troopa plan create --json --project 1 --title "Checkout" --agent claude
troopa plan add-step --json --id 1 --title "Página del carrito"
troopa profile create --json --name Ana --profession Chef
troopa run rounds --json --id 3
troopa brain sync --json

Recursos: project, client, task, run, plan, profile, brain. La referencia completa está en docs/cli-json.md.
